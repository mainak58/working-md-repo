Partitioning means taking one logical dataset and physically breaking it into smaller pieces — while the application keeps believing it is still one table. There are exactly two directions you can tear.

tear the sheet

No cut. All 4 users, all 4 columns, one place.

Tearing across rows is horizontal partitioning — every piece keeps the same columns but holds different users. Tearing down columns is vertical partitioning — every piece keeps all the users but holds different fields. Try both at once: real systems often do.

demo 01 · horizontal partitioning

Where does row 7 live?

This is what people usually mean by partitioning, and it is your option 2. The catch is that you cannot just put "50 rows here, 50 rows there." You need a rule that lets the application work out which database holds a user without searching for it. That rule is the partition key. Pick a strategy and watch the same 12 users land differently.

strategy shards

Add signups while range is selected. Every new user has a higher id than every old one, so they all pile into the last shard — three machines sit idle while one absorbs the entire write load. That is a hot spot, and it is the reason range partitioning by id is usually a trap. Range by time is a different story: it is the most common partitioning scheme in production, because "last 7 days" then touches one partition instead of five years of history, and deleting old data becomes an instant DROP PARTITION.

demo 02 · the cost of growing

Adding a shard moves your data

Hash spreads load beautifully — until you need a third machine. If your rule is hash(id) % 2 and it becomes hash(id) % 3, almost every row is suddenly on the wrong box and has to physically move. The fix is to hash into a fixed number of virtual buckets first, then map buckets onto machines. Watch the difference.

mapping grow to

Sitting on 2 shards. Grow to 3 and count the rows that have to move.

Same hash function, same keys, wildly different migration cost. With buckets you only reassign whole buckets, so going from 2 to 3 machines moves roughly a third of the data instead of two thirds — and you can move it bucket by bucket while the system stays online. Use a real hash here (MD5, MurmurHash, xxHash), never a language's built-in string hash and never Math.random.

demo 03 · vertical partitioning

The columns nobody reads

The third option you did not list. Databases do not read single rows off disk — they read fixed-size pages, 8 KB at a time. If every row drags a 1.2 KB bio and an 800-byte preferences blob along with it, then SELECT id, email hauls all of that through disk and memory just to throw it away.

table
One 8 KB page holds 3 rows — 2,116 bytes each.
Reading id + email for 10,000 users: 3,334 pages off disk.

Splitting users into a narrow users_core and a wide users_profile means far more useful rows fit per page, so the queries you run constantly get dramatically cheaper. The cold table is still there, joined by id, for the rare page that actually needs a bio.

demo 04 · your option 1

Splitting by feature is not sharding

Putting users in db1 and courses in db2 is real and useful — it is called functional partitioning, or "database per service." But notice what it does and does not buy you.

One database. Every table can join freely with every other table.

You have split the schema, not any individual dataset. If users grows to 500 million rows, db1 is right back to being overloaded and you have gained nothing on that front. What you did gain is isolation: the two workloads can be tuned, backed up, and scaled independently. It is usually the right first move because it is simple and reversible — just don't mistake it for a fix for table size.

demo 05 · life after sharding

Some queries get expensive

Once rows live on four machines, the shape of a query decides its cost. A lookup by the shard key is one hop. Anything else fans out to every shard, and your latency becomes the slowest shard, not the average one.

user id
Pick a query above.

This is also where joins break. If users are sharded by user_id and courses by course_id, then "which courses is user 7 enrolled in" may have to hit both databases and join the results in your application code. The standard defence is co-location: pick one shard key for all related data — usually tenant_id or org_id — so everything one customer touches lives on one machine.

Three more things that break, in rough order of how much they will hurt: transactions cannot span shards, so you need sagas or two-phase commit. Auto-increment ids collide, so you need UUIDs or a Snowflake-style generator. And changing the shard key later is close to impossible — this is the most consequential decision in the whole exercise.

closing · the order to do things

You have 200 rows. Do none of this.

This is the most useful sentence on the page. Postgres or MySQL on a modest server handles tens of millions of rows on a single node without complaint. Partitioning starts paying off somewhere north of 50–100 million rows, or when a table no longer fits in RAM. Sharding is for when one machine genuinely cannot hold your data or absorb your writes. Work down this list in order, and stop as soon as the problem goes away — most applications never get past rung three.

  1. Index and optimiseRead the query plan. A missing index beats a new machine, every time.
  2. Pool connections and cacheRedis in front of the hot reads. Cheapest order-of-magnitude you will ever buy.
  3. Add read replicasSends reads elsewhere. Does nothing for writes, and introduces replication lag.
  4. Split by featureYour option 1. Simple, reversible, and it isolates workloads from each other.
  5. Partition inside one databaseDeclarative partitioning. The database manages the pieces; your queries never change.
  6. Shard across machinesYour option 2, for real. Reach for Citus or Vitess before you hand-roll a router.

The code, when you actually get there

Postgres, range partitioned by time — the partition key must be part of every unique constraint, which is why the key sits inside the primary key:

CREATE TABLE orders (
    id          bigserial,
    user_id     bigint      NOT NULL,
    created_at  timestamptz NOT NULL,
    PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

CREATE TABLE orders_2026_08 PARTITION OF orders
    FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');

Create future partitions before rows need them or inserts fail — automate it with pg_partman rather than a cron job you will forget. Then run EXPLAIN on a query filtered by created_at and confirm it touches one partition. That pruning is the entire point; if it is not happening, the partitioning is doing nothing for you.
